# سیستم رهگیری زنجیره (TraceChain) - پیاده‌سازی آموزشی زمان‌اجرا (Runtime) به زبان Rust

این پروژه یک پیاده‌سازی ساده و آزمایشی از زمان‌اجرا (Runtime) زنجیره‌بلوکی الهام گرفته از معماری‌های Polkadot و Substrate به زبان Rust است. این مخزن به عنوان نسخه موازی پروژه آموزشی Cosmos/Go ما طراحی شده است و مفاهیم بنیادی انتقال دارایی، مدیریت حساب، صندوق‌های نقدینگی (Vaults) و تراکنش‌های اتمی (Atomic Transactions) را با زبان ساده آموزش می‌دهد.

---

## نگاشت ساختاری: از Cosmos/Go به Polkadot/Rust

در جدول زیر معادل‌های استفاده شده بین پروژه آزمایشی Go/Cosmos و نسخه Rust/Polkadot را مشاهده می‌کنید:

| مدل آموزشی Go / Cosmos | مدل آموزشی Rust / Polkadot | توضیح مفهومی |
| :--- | :--- | :--- |
| `BankState` | `BankState` | ساختار ذخیره‌سازی موجودی حساب‌ها |
| `BankKeeper` | `BankModule` | ابزار مدیریت منطق انتقال موجودی |
| `VaultState` | `VaultState` | ساختار ذخیره‌سازی سهم‌ها و کل دارایی‌های صندوق |
| `VaultKeeper` | `VaultModule` | منطق واریز دارایی و برداشت سهم‌ها (مشابه استاندارد ERC-4626) |
| `AccountState` | `AccountState` | ساختار ذخیره‌سازی شماره‌های ترتیب تراکنش‌ها (Nonces) |
| `AccountKeeper` | `AccountModule` | ابزار بررسی و افزایش شماره ترتیب تراکنش برای جلوگیری از حملات تکرار |
| `Message` | `RuntimeCall` | نوع چندریختی (Enum) برای دستورات زمان‌اجرا |
| `MsgDeposit` | `RuntimeCall::Deposit` | درخواست واریز دارایی به صندوق نقدینگی |
| `MsgWithdraw` | `RuntimeCall::Withdraw` | درخواست سوزاندن سهم‌ها و دریافت دارایی از صندوق |
| `Tx` | `Transaction` | تراکنش فرستاده شده که شامل امضاکننده، nonce و مجموعه‌ای از دستورات است |
| `Sequence` | `nonce` | شناسه عددی یکتا برای هر تراکنش جهت حفظ ترتیب و اتمی بودن |
| `AnteHandler` | `TransactionValidator` | بررسی صحت امضاها و nonce تراکنش پیش از اجرا |
| `BaseApp` | `Runtime` | هسته مرکزی زمان‌اجرا هماهنگ‌کننده کل فرآیند و به‌روزرسانی حالت زنجیره |
| `Clone / Cache / Commit / Rollback` | `Clone / Cached RuntimeState / Commit / Rollback` | کپی‌سازی از حالت جاری، تلاش برای اجرا، تایید نهایی در صورت موفقیت کامل یا بازگشت به حالت قبل در صورت شکست |

## مقایسه نحو و ویژگی‌ها بین Go و Rust

برای سهولت یادگیری فراگیرانی که از دنیای Go به Rust سفر می‌کنند، نکات کلیدی زیر آورده شده است:

### ۱. نگاشت نوع داده‌ها

* **در Go:**
  ```go
  map[string]uint64
  ```
  **در Rust:**
  ```rust
  HashMap<String, u64>
  ```

* **در Go:**
  ```go
  []Message
  ```
  **در Rust:**
  ```rust
  Vec<RuntimeCall>
  ```

* **در Go:**
  ```go
  results = append(results, res)
  ```
  **در Rust:**
  ```rust
  results.push(result)
  ```

### ۲. مدیریت خطا و مقادیر خالی

* **در Go:**
  ما از نوع داده بازگشتی `error` استفاده می‌کنیم و آن را با `nil` مقایسه می‌نماییم:
  ```go
  res, err := function()
  if err != nil {
      return err
  }
  ```
* **در Rust:**
  ما از سیستم پیشرفته `Result<T, E>` استفاده می‌کنیم که دارای دو شاخه `Ok(value)` و `Err(error)` است. همچنین عملگر کوتاه‌نویسی `?` به ما اجازه می‌دهد در صورت بروز خطا، بلافاصله آن را به بیرون تابع بفرستیم:
  ```rust
  let result = function()?;
  ```

* **در Go:**
  برای مقادیر اختیاری که ممکن است وجود نداشته باشند از اشاره‌گرهای تهی (`nil`) استفاده می‌شود.
* **در Rust:**
  از سیستم ایمن `Option` استفاده می‌شود که دو حالت دارد: `Some(value)` و `None`. این الگو ما را مجبور می‌کند که به صورت صریح تمام حالات را با `unwrap_or` یا ساختار `match` هندل کنیم.

### ۳. مدیریت حافظه: مالکیت (Ownership)، ارجاع‌ها و طول‌عمرها

* **اشاره‌گرها در مقابل ارجاع‌ها**:
  Rust به جای Garbage Collector از سیستم مالکیت (ownership) و مرجع‌دهی (borrowing) استفاده می‌کند.
  * ارجاع غیرقابل‌تغییر (`&`): به شما اجازه خواندن همزمان داده را می‌دهد.
  * ارجاع قابل‌تغییر (`&mut`): اجازه نوشتن اختصاصی بر روی داده را می‌دهد و در زمان وجود آن، هیچ مرجع دیگری نمی‌تواند فعال باشد.
* **طول‌عمرها (Lifetimes)**:
  استفاده از `'a` یا `'_` تضمین می‌کند که ساختارهایی مانند `BankModule<'a>` یا `VaultModule<'a>` که مراجع داده‌ها را در خود نگه می‌دارند، هیچ‌گاه بیشتر از خود داده‌ی اصلی در حافظه زنده نمانند. این موضوع امنیت در اجرای موازی و دسترسی به حافظه را در زمان کامپایل تضمین می‌کند.

### ۴. اتمی بودن و کپی صریح حالت

ما از قابلیت کلون‌سازی عمیق در Rust بهره برده‌ایم:
```rust
#[derive(Clone)]
```
این قابلیت به ما اجازه می‌دهد کلون کاملاً مستقل و عمیقی از حالت ایجاد کنیم:
```rust
let mut cached_state = self.state.clone();
```
چون `HashMap` در Rust خودش مالک کلیدها و ارزش‌های داخلی‌اش است، عمل `clone()` یک کپی صددرصد ایزوله می‌سازد. تراکنش ابتدا روی این حالت کپی‌شده موقت اجرا می‌شود. اگر تمام عملیات موفقیت‌آمیز بود، این حالت موقت تبدیل به حالت اصلی زمان‌اجرا (Commit) می‌شود؛ در غیر این صورت، حالت شبیه‌سازی‌شده دور ریخته شده و حالت قبلی بدون تغییر باقی می‌ماند (Rollback).

## آموزش جامع احراز هویت تراکنش‌ها (Transaction Authentication)

در این فاز، سیستم زمان‌اجرا (Runtime) آموزشی خود را به قابلیت احراز هویت رمزنگاری تراکنش‌ها مجهز کرده‌ایم. در ادامه مفاهیم کلیدی این بخش به زبان ساده توضیح داده شده است:

### ۱. کلید عمومی (Public Key) و کلید خصوصی (Private Key)
در رمزنگاری نامتقارن، هر کاربر دارای یک جفت کلید است:
- **Private Key**: کلید مخفی که فقط در اختیار مالک حساب (یا Wallet) است و برای تولید امضا استفاده می‌شود. این کلید تحت هیچ شرایطی نباید در حالت زمان‌اجرا (RuntimeState) ذخیره یا ارسال شود.
- **Public Key**: کلید عمومی که در دسترس همگان (از جمله RuntimeState) قرار دارد و برای تایید صحت امضاها استفاده می‌شود. در این پیاده‌سازی، Public Key هر امضاکننده درون ساختار `AccountState` ذخیره می‌شود.

### ۲. بایت‌های امضا (SignBytes) و رمزگذاری معین (Deterministic Encoding)
- **SignBytes**: داده‌های تراکنش است که به صورت سریال شده تبدیل به برداری از بایت‌ها (`Vec<u8>`) می‌شوند تا برای امضا ارسال گردند. فیلد `signature` خود نباید جزوی از `SignBytes` باشد.
- **Deterministic Encoding**: تضمین می‌کند که یک تراکنش مشخص با مقادیر یکسان همیشه بایت‌های سریال‌شده یکسانی تولید کند. این رفتار برای ثبات و تایید یکسان امضاها در سراسر نودهای شبکه ضروری است.

### ۳. رمزگذاری با پیشوند طول (Length-prefix Encoding)
برای جلوگیری از تداخل فیلدها و ابهام در الحاق رشته‌ها (Ambiguous Concatenation)، هر رشته را با قانون زیر به بایت تبدیل می‌کنیم:
`[طول رشته به عنوان u64 Big Endian] [بایت‌های UTF-8 رشته]`
این ویژگی تضمین می‌کند که الحاق فیلدهایی مانند "ab" + "c" با "a" + "bc" متمایز و بدون ابهام باشد.

### ۴. شناسه زنجیره (Chain ID)
جهت تفکیک قلمروهای مختلف شبکه (Domain Separation) و جلوگیری از حملات بازپخش تراکنش یک زنجیره روی زنجیره دیگر، `Chain ID` به صورت صریح جزو ورودی‌های تولید بایت‌های امضا (`SignBytes`) قرار می‌گیرد. یک تراکنش امضا شده برای `"tracechain-1"` روی `"tracechain-2"` معتبر نخواهد بود.

### ۵. احراز هویت (Authentication) در مقابل مجوز دسترسی (Authorization)
- **Authentication**: پاسخ به این سوال که "چه کسی این تراکنش را امضا کرده است؟" که از طریق تایید صحت رمزنگاری امضا انجام می‌شود.
- **Authorization**: پاسخ به این سوال که "آیا فرستنده تراکنش اجازه اجرای این دستور را دارد؟" به عنوان مثال، تراکنشی که توسط Amir امضا شده است نمی‌تواند دستور برداشت از دارایی‌های Ali را اجرا کند، حتی اگر امضای Amir صددرصد معتبر باشد.

### ۶. محافظت در برابر بازپخش (Replay Protection) با استفاده از Nonce
تکنیک استفاده از `Nonce` (شماره ترتیب تراکنش) تضمین می‌کند که هر تراکنش منحصر‌به‌فرد بوده و فقط یک بار قابل اجراست. پس از اجرای موفقیت‌آمیز تراکنش، مقدار `Nonce` حساب ارتقا یافته و تلاش برای ارسال مجدد تراکنش قبلی با خطای `"invalid nonce"` رد خواهد شد.

### ۷. تفاوت `Vec<u8>` و `&[u8]`
- **`Vec<u8>`**: یک ساختار پویا و مالک بر روی حافظه Heap است که به ما اجازه می‌دهد داده‌ها را ذخیره، تغییر، یا بازگردانیم. فیلد `signature` تراکنش یک نمونه از آن است.
- **`&[u8]`**: یک مرجع غیراستخدامی و موقت (Slice) به داده‌های بایت است و هیچ مالکیتی ندارد، که برای بهینه‌سازی دسترسی خواندن بدون کپی‌کاری استفاده می‌شود.
